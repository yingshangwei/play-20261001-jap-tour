# 酒吧搜索模块需求

## 文档入口

- [仓库文档地图](../../../MAP.md)
- [需求文档索引](../index.md)
- [多攻略配置平台需求](../guide-platform/requirements.md)

## 目标

让旅行者按当天所在区域、计划到店时间和临时偏好搜索可实际前往的酒吧。结果必须优先保证当时营业、位置顺路和能够安全返回住宿地，而不是只按评分或热度排序。

## 范围

- 支持从当天手账中的酒店、景点或餐厅带入搜索区域，也允许手动输入区域或地点。
- 支持指定日期、预计到店时间、停留时长和最晚离店时间。
- 支持按酒吧类型、预算、氛围、酒类偏好、是否需要预约、同行人数和步行距离筛选。
- 每次搜索都基于当次请求重新获取候选，不保存个人画像、偏好历史或外部推荐知识库。
- 只提供信息、地图和预约入口，不代订、不提交个人信息。

## 功能要求

1. 搜索必须至少接收地点和预计到店时间；缺少日期时默认使用当前打开手账的日期，并明确展示该默认值。
2. 返回 3–5 个有效候选，并列出名称、类型、所在区域、从起点出发的预计耗时、营业时间、最后点单或最晚入店信息、价格区间、费用提示、预约要求和适合原因。
3. 每个候选必须提供可直接打开的地图链接；存在官方页面或官方预约页时一并提供。
4. 排序优先级依次为：目标时段可用、地理顺路、返程安全、约束匹配、口碑。不能只因评分高而推荐绕路地点。
5. 对营业时间、临时休业、包场、座位费、服务费、最低消费、吸烟规则或预约条件无法确认的字段，必须显示“未核实”，不得补全或猜测。
6. 晚间搜索必须结合当天住宿地给出建议离店时间、最后一班可完整返店的公共交通边界，以及错过末班后的出租车备选。
7. 搜索结果必须显示资料来源和核对时间；过期结果再次打开时提示重新搜索。
8. 结果与当天固定行程冲突时，说明会替换或压缩哪个可选停靠点，不得移动 `AGENTS.md` 中的不可删除锚点。
9. 对不适用、已关闭、目标时段无法进入或无法确认关键信息的候选，应隐藏或降级到“待核实”，不能混入首选结果。
10. 搜索和展示过程遵守当地年龄、场所规则和安全要求；饮酒后不推荐驾车或骑行返程。

## 状态与异常

- **初始状态**：解释需要地点和到店时间，可从当天手账带入。
- **搜索中**：保留已输入条件，并说明正在核对营业与返程信息。
- **无结果**：说明是时段、距离还是筛选条件造成，并允许放宽一项条件后重试。
- **资料不足**：保留地图入口，但清楚标记尚未核实的字段，不生成确定性结论。
- **网络或来源异常**：不展示旧数据为当前结果；允许用户稍后重试或直接打开地图搜索。

## 边界与待确认

- [需要确认] 酒吧搜索的首个 UI 入口位于首页、当天手账，还是两处都提供。
- [需要确认] 默认包含哪些场所类型，以及是否需要排除夜店、会员制店或其他特殊业态。
- [需要确认] 默认搜索半径、预算分档和最晚返店安全余量。
- 具体搜索服务、天气或地图供应商、缓存时长和数据模型属于开发设计，不在本需求中决定。

## 验收标准

- 能从手账地点带入区域和日期，也能手动完成一次搜索。
- 每个首选候选都有营业证据、位置、费用提示、官方或地图链接及核对时间。
- 已关闭、目标时段不营业和明显无法安全返店的场所不会排在首选中。
- 改变到店时间、预算或距离后，结果和排序会相应更新。
- 无结果、资料不全和网络失败都有明确可恢复状态。
- 桌面和移动端均可完成筛选、查看候选和打开外部链接，键盘与读屏器可访问主要控件。
